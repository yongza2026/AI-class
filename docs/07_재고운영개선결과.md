# POCO 재고 운영 개선 결과

작성일: 2026-10-15
검증 범위: 로컬 가상 데이터
운영 배포: 하지 않음

## 1. 기존 구조에서 확인한 사실

- 판매 기록은 판매 당시의 식재료 원가와 포장 원가를 복사해 보관하므로, 이후 매입 단가가 바뀌어도 과거 판매 수익성이 바뀌지 않는다.
- 재고는 초기 재고 또는 최근 실사를 기준으로 이후 입고·폐기·조정과 판매 레시피 사용량을 합산한다.
- 기존 `/inventory/new`는 신규 품목 생성 화면이 아니라 기존 품목의 재고 변동 입력 화면이었다.
- 자료는 브라우저 IndexedDB에 저장되며, 환경변수가 설정된 경우에만 Supabase 공용 저장소를 사용한다.
- 기존 JSON 백업은 스키마 1 버전이었다. 이번 확장 자료는 스키마 2로 저장하되 1 버전 백업도 자동 보완해 읽는다.

## 2. 최종 메뉴와 주요 화면

- 대시보드
- 판매·손익: 판매 기록, 메뉴 수익성
- 재고·구매: 재고 현황, 품목 관리, 제조 배치, 구매·원가
- 운영: 운영 비용, 데이터 관리

기존 주소(`/inventory`, `/inventory/new`, `/costs` 등)는 유지했다. 새 주소는 `/inventory/items`, `/inventory/batches`다.

## 3. 구현 내용

- 빈 자료 상태에서도 첫 품목 생성
- 분류 6종, 구매/자체 제조, 기준 단위, 구매 단위와 포장 용량, 낱개 소수 허용, 공급처, 위치, 안전·목표 재고, 활성 상태 관리
- 이름·브랜드가 같은 품목 후보 안내와 규격이 다른 품목 분리
- 이력이 있는 품목의 기준 단위 변경 차단, 삭제 대신 비활성화
- 서울 날짜를 입고·폐기·실사의 기본 날짜로 사용
- 입고의 기준 수량 입력과 구매 포장 입력 지원
- `700ml × 3병 = 2,100ml` 환산, L↔ml 및 kg↔g만 자동 환산
- 구매금액을 비우면 무료 매입이 아니라 `미입력` 상태로 저장
- 입고와 구매 로트, 재료 단가 이력을 연결하고 구매·원가 화면에서 미입력 금액 보완
- 입고한 병의 미개봉 수를 보존하고 1병 개봉 시 상태·개봉일·위치를 기록
- 폐기 수량의 현재 재고 초과 차단 및 폐기 사유 필수
- 실측 수량은 빈칸으로 시작하며 0을 허용하되 확인 절차 적용; 차이가 크면 조정 사유 필수
- 저장 전 적용 전·변동·적용 후 수량과 입고 단가 미리보기
- 자체 제조 배치에서 원재료 차감, 완성 재고 증가, 실제 수율과 제조 원가 연결
- 제조 중 수량과 사용 가능 수량 분리
- 기록별 UUID, 출처 ID와 변경 전후 감사 이력 추가
- 판매 외 수동 사용은 사유를 필수로 받고, 같은 날 같은 재료의 판매 자동 차감이 있으면 중복 여부를 다시 확인
- 분류·위치·부족 재고 필터와 모바일 하단 메뉴 가로 스크롤 적용
- 로그인 확인 메일이 현재 사이트로 돌아오도록 리다이렉트 주소 지정

## 4. 계산 기준

- 구매 현금 지출과 판매에 사용한 재료 원가는 서로 다른 지표다. 구매금액을 운영비에 다시 넣지 않는다.
- 입고 단가 = 부가세 포함 구매 총액 ÷ 기준 단위 환산 수량
- 판매 원가는 판매일 이하에서 가장 최근인 단가를 사용해 판매 기록에 복사한다.
- 판매 후 재고는 레시피 사용량으로 자동 차감한다. `수동사용`은 판매 외 사용만 기록해야 한다.
- 제조 원가 = 실제 투입 원재료의 제조 시작일 기준 단가 합계
- 완성품 단가 = 제조 원가 ÷ 실제 완성량
- 발주 참고량은 설정된 목표 재고를 우선 사용하고, 없으면 최근 28개 마감 영업일 사용량과 리드타임·안전일로 계산한다.

## 5. 자료 마이그레이션과 복구

- 기존 자료를 읽을 때 `purchaseLots`, `productionBatches`, `bottleStates`, `auditLog`가 없으면 빈 목록으로 추가한다.
- IndexedDB는 2버전으로 올라가며 기존 표와 ID, 수량, 금액은 유지된다.
- JSON 1버전 백업은 2버전 구조로 자동 보완해 복원한다. 새 백업은 2버전으로 내려받는다.
- 문제 발생 시 작업 전 JSON 백업을 복원하면 기존 핵심 자료로 되돌릴 수 있다.
- Supabase용 SQL 변경 파일은 버전별로 분리했다. 이번 작업에서는 운영 배포와 운영 데이터 입력을 하지 않았다.

## 6. 검사 결과

- `npm test`: 3개 파일, 15개 테스트 통과
- `npm run typecheck`: 통과
- 변경 파일 ESLint: 오류·경고 0건
- `npm run build`: 성공, 새 화면을 포함한 15개 정적 경로 생성
- Playwright 로컬 클릭 검사: 통과
  - 빈 상태 첫 품목 생성
  - 700ml 3병을 2,100ml로 환산
  - 구매금액 미입력 상태 확인
  - 현재 재고를 넘는 폐기의 저장 차단
- 실제 운영 사이트, 실제 Supabase 데이터, 실기기 모바일 화면은 검사하지 않았다.

## 7. 아직 구현하지 않은 사항

- 여러 품목을 한 화면에서 연속 실사하는 전용 표
- 병별 잔량 직접 수정과 개봉 병 선택 사용
- 제조 실패 시 일부 수율만 확정하거나 격리·폐기로 전환하는 전용 흐름
- 기존 매입 전표를 입고 기록에 수동 연결하는 선택 화면
- Excel에서 신규 로트·배치·병·감사 이력을 완전히 왕복하는 확장 양식
- 모든 모달의 완전한 키보드 초점 순환 제한
- 사용기한 임박 필터와 대시보드 카드

## 8. 운영 배포 전 확인 사항

1. 운영 자료 전체 JSON 백업
2. 별도 미리보기 배포에서 실제 파일 사본으로 가져오기·복원 검사
3. Supabase 인증 리다이렉트 URL과 관리자 이메일 확인
4. 새 SQL 마이그레이션 보안 검토 및 적용 여부 결정
5. 360×800, 390×844 실기기 확인
6. 미구현 항목 중 매장 운영에 먼저 필요한 순서를 결정한 뒤 추가 구현
