# POCO 월간 성과 지표와 운영 개선 제안

작성일: 2026-10-22

## 1. 참고 자료와 현재 확인한 사실

- 참고: 사용자 제공 `오세정(강의자료).pdf` 19~23쪽, 26쪽, 57~58쪽.
- 강의는 객단가·회전율·시간대별 매출·메뉴 순위와 함께, 매출 변화의 이유를 찾고 운영을 개선하는 습관을 강조한다. 57쪽에는 동일 매장 매출 성장률, 좌석 시간당 매출, 재방문 매출 비중을 소개한다.
- 현재 앱은 매장별 공용 저장소에서 날짜·메뉴·수량·실 결제금액·판매 당시 원가·수수료를 읽는다. 월별 매출과 전년 동월 비교에 필요한 판매일·금액이 이미 있다.
- 영업 달력에는 영업 여부와 기록 마감 여부가 있다. 기존 월별 손익·메뉴 수익성·재고·폐기 기록도 재사용할 수 있다.
- 영수증 번호·손님 수·주문 시각·입퇴장 시각·좌석 수·고객 방문 식별자는 현재 표준 판매 기록에 없다. 메뉴별 판매 행 수는 결제 건수나 고객 수가 아니다.
- 제공된 매장 샘플은 가상 자료다. 샘플의 매출을 실제 POCO 실적으로 해석하면 안 된다.

## 2. 이번에 구현한 월간 성과 화면

대시보드에 최근 12개월의 매출·전년 같은 달 매출을 나란히 보여 주는 그래프와 상세 표를 추가했다. 기존 매출 계산이나 저장 구조를 바꾸지 않고 조회 시 집계한다.

- 기준 날짜가 속한 달을 마지막으로 12개월을 표시한다. 일·주·월 화면 선택과 무관하게 월간 패널은 월 단위로 유지한다.
- 조회 범위는 기준 날짜와 매장 자료 기준일 중 더 이른 날짜까지만 포함한다. 이전 달은 월 전체, 마지막 진행 중인 달은 해당 일자까지 집계한다.
- 진행 중인 달은 전년도 같은 월의 같은 일자까지 비교한다. 예: 2026-10-01~18 ↔ 2025-10-01~18.
- 완료된 달은 각각 월 전체를 비교한다. 윤년의 완료된 2월은 28일과 29일의 차이를 포함한다. 월중 비교에서 전년도에 해당 일자가 없으면 그달 말일로 맞춘다.
- 매출은 기존 `netSales` 합계다. 할인 후 실제 결제금액이며 세금 포함 여부도 원본 금액 기준을 그대로 따른다. 원가나 수수료를 다시 빼지 않는다.
- 성장률 = (이번 매출 − 전년 매출) ÷ 전년 매출 × 100. 매출 차액도 함께 표시한다.
- 전년 자료 없음과 전년 매출 0원을 구분한다. 전년이 없거나 0원이면 성장률을 만들지 않는다. 현재 자료가 없는 달도 임의로 0원이나 −100%로 만들지 않는다.
- 기록이 실제로 존재하면 미마감 판매도 매출에 포함하되 비교 상태를 ‘잠정’으로 표시한다. 모든 날짜가 마감 또는 판매 없는 휴무로 확인된 기간은 확정으로 본다. 매장 자료 시작일 이전에 걸친 기간은 확정으로 보지 않는다.
- 같은 매장 기준이지만 가격 인상·휴무일 수·날씨·프로모션 영향이 자동으로 제거되는 것은 아니다. 다점포가 생길 경우 비교 가능한 기존 점포 집합을 정하는 기준이 추가로 필요하다.

예: 2025년 10월 100만원, 2026년 10월 120만원이면 +20%. 2026년 10월 18일 누적을 2025년 10월 전체와 비교하지 않는다.

## 3. 다음 개선 우선순위 — 제안이며 추가 구현하지 않음

| 우선순위 | 제안 | 판단할 수 있는 일 | 필요한 기록 |
|---|---|---|---|
| 1 | 월 마감 점검 + 영업일당 매출 | 매출 감소가 휴무 증가 때문인지, 하루 장사가 약해졌는지 구분 | 기존 영업 달력과 일별 매출. 누락·휴무·실제 0원 확인 필요 |
| 2 | 메뉴별 매출 변화와 공헌이익 변화 | 잘 팔리지만 이익이 적은 메뉴, 주력 메뉴 매출 감소 탐지 | 기존 판매·레시피·판매 당시 원가 활용 |
| 3 | 월간 개선 일지 | 문제 하나 → 실행한 변경 → 다음 달 결과를 연결 | 문제·가설·실행일·담당자·비교 기간·결과를 기록하는 기능 추가 필요 |
| 4 | POS 영수증 단위 가져오기 | 결제 1건당 금액, 주류·푸드 동시 주문, 시간대별 매출 파악 | 영수증 ID·결제 일시·취소/환불·메뉴 행. 실제 POS 내보내기 파일 검토 필요 |
| 5 | 방문·좌석·재방문 분석 | 객단가·좌석 효율·단골 매출 파악 | 인원·좌석 수·운영시간·입퇴장·방문 식별 기록 필요. 개인정보 처리 범위 별도 결정 |

POCO에는 우선 1~2번을 권장한다. 고객 정보를 새로 수집하지 않고 현재 자료를 더 유용하게 쓰는 방향이다. 객단가·빌단가·회전율·재방문율은 필요한 기록을 확보한 뒤 추가한다.

예시: 월 매출 +10%인데 영업일 +20%라면 일평균 매출은 하락했을 수 있다. 반대로 매출이 올라도 재료 원가 상승이나 할인 증가로 공헌이익은 줄 수 있다. 숫자는 원인을 단정하는 답이 아니라 확인할 문제를 고르는 기준으로 사용한다.

## 4. 추천 운영 루틴

- 매일: POS 일 매출과 홈페이지 기록을 대조하고 실제 0원·휴무·누락을 구분한다.
- 매주: 감소한 메뉴·품절·폐기를 함께 보고 준비량이나 판매 제안을 한 가지 바꾼다.
- 매월: 마감 자료로 전년 같은 달·영업일당 매출·남는 돈을 확인하고 다음 달 실험 한 가지를 정한다.

## 5. 적용 범위와 남은 확인

로컬 구현이며 운영 배포는 별도 단계다. 공용 DB 구조·권한·운영 자료를 변경하지 않는다. 자료가 없는 지표를 추정값으로 대신하지 않는다. 신규 개인정보 수집, POS 연동, 추가 지표와 개선 일지 저장은 제안 범위로 남긴다.
