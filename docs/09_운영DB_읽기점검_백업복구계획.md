# 운영 DB 읽기 점검과 백업·복구 계획

작성일: 2026-10-15  
대상: Supabase `POCO Operations` (`ap-northeast-2`)  
점검 원칙: 조회만 수행했으며 운영 자료를 추가·수정·삭제하지 않았다.

## 1. 확인된 사실

### 서비스와 요금제

- 프로젝트 상태는 `ACTIVE_HEALTHY`, PostgreSQL은 17.11이다.
- 조직은 Free 요금제다. 따라서 유료 요금제의 자동 일일 백업이나 시점 복구를 당연히 사용할 수 있다고 전제하면 안 된다.
- 공개 스키마의 6개 표 모두 행 단위 접근 제한(RLS)이 켜져 있다.
- 현재 매장은 1개, 허용 사용자 2명, 가입된 매장 사용자 2명이다.

### 저장 구조

- 운영 자료는 `store_records` 한 표에 `collection`, `record_key`, `payload(JSON)` 형태로 저장된다.
- `store_datasets`에는 데이터 묶음의 설명과 버전이 저장된다. 현재 버전은 2이고 자료 구분은 `가상 매장 샘플`이다.
- 현재 저장된 레코드는 11,852건이다.
- 저장 함수 `replace_store_dataset`은 한 번에 기존 레코드를 모두 지우고 새 자료를 다시 넣는다. 한 번의 DB 작업으로 묶여 중간 실패에는 안전하지만, 두 사용자가 동시에 저장하면 먼저 저장한 사람의 변경이 사라질 수 있다.

### 연결 무결성

다음 연결에서 존재하지 않는 ID는 모두 0건이었다.

- 재고 이력 → 품목
- 기초 재고 → 품목
- 가격 이력 → 품목
- 레시피 → 메뉴 및 품목
- 판매 → 메뉴

### 권한과 보안

- 매장 구성원은 조회할 수 있고, `owner`와 `editor`는 자료를 수정할 수 있다.
- `viewer`도 현재 화면에서는 편집 버튼을 볼 수 있지만 DB가 저장을 거부한다. 화면에서도 권한에 따라 버튼을 숨기거나 비활성화해야 한다.
- 관리자 승인 요청은 본인과 매장 owner만 조회할 수 있다.
- Supabase 보안 점검 경고는 유출된 비밀번호 차단 기능이 꺼져 있다는 1건이다. 운영 전 [비밀번호 보호 설정](https://supabase.com/docs/guides/auth/password-security#password-strength-and-leaked-password-protection)을 켜는 것이 좋다.
- 사용되지 않은 인덱스 6건은 프로젝트 생성 직후라 사용 통계가 충분하지 않을 수 있다. 지금 삭제하지 않는다.

## 2. 반드시 먼저 해결할 문제

현재 DB의 `store_records.collection` 제한에는 아래 4종이 없다.

- `purchaseLots`
- `productionBatches`
- `bottleStates`
- `auditLog`

앱은 이 자료를 저장하려고 하지만 DB는 거부할 수 있다. 기존 제한을 무작정 넓혀 장기 사용하기보다, 2단계의 전용 표로 옮길 때까지 임시 호환 변경이 필요한지 별도로 판단한다.

## 3. 변경 전 백업 절차

Free 요금제에서는 앱 백업과 DB 논리 백업을 둘 다 만든다. Supabase의 일반 백업 안내는 [공식 문서](https://supabase.com/docs/guides/platform/backups)를 따른다.

1. 앱의 `데이터 관리`에서 전체 JSON 백업을 내려받는다.
2. 파일명은 `poco-before-phase2-YYYYMMDD-HHmm.json`으로 저장한다.
3. 같은 파일을 서로 다른 두 위치에 보관한다. 예: 매장 PC와 암호화된 클라우드 폴더.
4. 백업 파일을 다시 가져오기 화면에서 읽되, 실제 적용 직전 미리보기까지만 진행한다.
5. 표별 건수와 위 지문을 다시 기록한다.
6. Supabase CLI 또는 대시보드가 제공하는 논리 백업을 별도로 만든다. 서비스 역할 키는 브라우저나 저장소에 넣지 않는다.

## 4. 복구 절차

### 앱 자료만 잘못된 경우

1. 사이트 입력을 잠시 중단한다.
2. 오류 발생 시각과 마지막 정상 저장 시각을 기록한다.
3. 정상 JSON 백업을 미리보기로 검사한다.
4. 표별 건수, 매장명, 기준일을 확인한 뒤 owner가 복원한다.
5. 판매 합계, 재고 잔량, 메뉴 원가를 변경 전 기준값과 비교한다.

### 스키마 변경이 잘못된 경우

1. 새 화면 사용을 중지하고 기존 JSON 저장 화면으로 되돌린다.
2. 새 표는 즉시 삭제하지 않고 읽기 전용으로 보존한다.
3. 기존 `store_records`가 변경되지 않았는지 건수와 지문을 비교한다.
4. 새 표에만 기록된 내용이 있으면 역변환 목록을 만든 후 승인받아 복구한다.
5. 검증 완료 후에만 실패한 새 구조를 제거한다.
