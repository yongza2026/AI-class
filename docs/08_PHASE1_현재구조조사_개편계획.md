## 1. 현재 확인된 문제

### 1.1 현재 라우트와 화면 — 확인

| 현재 URL | 화면 | 주로 읽는 자료 | 저장 방식 |
|---|---|---|---|
| `/` | 대시보드·손익 | 판매, 비용, 재고, 달력 | 조회 전용 |
| `/sales`, `/sales/new` | 판매 조회·입력 | 메뉴, 레시피, 가격, 판매 | 판매 1건 저장·삭제 |
| `/profitability` | 메뉴 수익성 | 판매 당시 원가 스냅샷 | 조회 전용 |
| `/inventory` | 재고 현황·기록 | 품목, 초기재고, 판매, 재고 이벤트, 병 상태 | 전체 자료 교체 |
| `/inventory/items` | 품목 관리 | 품목, 공급사, 재고·레시피 참조 | 전체 자료 교체 |
| `/inventory/batches` | 제조 배치 | 품목, 가격, 재고 이벤트, 배치 | 전체 자료 교체 |
| `/costs` | 원장 업로드·품목·제품 원가 | 품목, 가격, 메뉴, 레시피 | 전체 자료 교체 |
| `/expenses` | 운영 비용 | 비용, 월 비용 계획 | 비용 1건 저장·삭제 |
| `/data` | 가져오기·백업·복원 | 전체 자료 | 전체 자료 교체 또는 삭제 |
| `/admin/access` | 가입 요청 승인 | Supabase 가입 요청·멤버 | 요청 승인·거절 |

현재 App Router에는 별도 API Route나 Server Action이 없다. 화면의 Client Component가 브라우저용 Supabase 클라이언트 또는 IndexedDB를 직접 호출한다.

직전 재고 통합 요청으로 로컬 작업 트리에 `/inventory/history`, 재고 탭, 통합 사이드바 변경이 **진행 중**이다. 아직 커밋·배포·브라우저 검증 완료 상태가 아니다.

### 1.2 현재 데이터 구조 — 확인

앱 내부 자료는 `CafeDataset` 한 묶음이며 다음 컬렉션을 가진다.

- 기준 정보: `suppliers`, `materials`, `menus`, `recipes`, `settings`
- 가격·영업 기준: `priceHistory`, `calendar`, `monthlyExpensePlan`
- 원장: `sales`, `openingInventory`, `inventoryEvents`, `expenses`
- 확장 자료: `purchaseLots`, `productionBatches`, `bottleStates`, `auditLog`

로컬에서는 Dexie/IndexedDB의 컬렉션별 테이블에 저장한다. 공용 저장소에서는 `store_datasets`에 메타 정보를, `store_records`에 `collection + record_key + JSON payload` 형태로 저장한다. 품목·레시피·판매·재고 사이의 연결은 DB 외래키가 아니라 JSON 안의 `materialId`, `menuId`, `recipeVersion`, `eventId`, `batchId`로 유지된다.

### 1.3 인증과 권한 — 확인

- Supabase 환경 변수가 있으면 로그인하지 않은 사용자는 로그인 화면을 먼저 본다.
- `store_members`의 역할은 `owner`, `editor`, `viewer`다.
- RLS는 매장 멤버만 조회하고 owner/editor만 수정하도록 구성되어 있다.
- 전체 교체 RPC는 클라이언트가 보낸 매장 ID를 쓰지 않고 로그인 사용자의 멤버십에서 대상 매장을 찾는다.
- 화면은 역할별로 수정 버튼을 숨기지 않는다. viewer도 입력 버튼을 볼 수 있으나 DB 정책에서 저장이 거절된다. 권한 확대는 아니지만 현장 사용자는 저장 단계에서야 권한 부족을 알게 된다.

### 1.4 재고 계산 — 확인

현재고 계산은 현재고 숫자를 매번 덮어쓰는 방식이 아니다.

1. 품목별 마지막 `실사조정`의 `countedQuantity`를 기준 잔량으로 삼는다. 실사가 없으면 `openingInventory`를 쓴다.
2. 기준일 이후의 입고·폐기·수동사용·제조투입·제조완성 이벤트를 합산한다.
3. 같은 기간 판매 기록에 저장된 레시피 버전과 수량으로 이론 사용량을 계산해 한 번 차감한다.
4. 최근 28개 마감 영업일의 판매 사용량으로 일평균 사용량·사용 가능 일수·부족 상태·발주 참고량을 계산한다.

판매 차감은 별도 `inventoryEvents`를 만들지 않고 계산 시 `sales`에서 직접 차감한다. 제조는 `inventoryEvents`에 투입 음수와 완성 양수를 생성한다. 따라서 현재 구조에서는 판매와 제조가 서로 다른 경로를 쓰며, 판매를 재고 이벤트로 추가 생성하면 이중 차감된다.

실사 입력 화면의 수량은 **증감량이 아니라 실제로 센 잔량**이다. 저장되는 `quantity`는 `실측 잔량 - 적용 전 잔량`, `countedQuantity`는 실측 잔량이다.

### 1.5 원가와 과거 기록 — 확인

- 판매 저장 시 당시 메뉴의 `recipeVersion`, 식재료 원가, 포장 원가, 결제수수료를 판매 기록에 스냅샷으로 저장한다.
- 메뉴 수익성은 이 스냅샷을 사용하므로 이후 가격 변경이 과거 판매 원가를 바꾸지 않는다.
- 입고는 재고 이벤트, 구매 로트, 가격 이력을 함께 만든다. 현재는 “매입 기록”과 “실제 입고 확정”이 하나의 저장 동작이다.
- 제조 배치는 투입 원가를 합산하고 실제 생산량으로 나눈 단가를 완성품 가격 이력에 추가한다.
- 메뉴 레시피가 자체 제조 베이스 품목을 참조하면 그 베이스의 단가만 메뉴 원가에 들어간다. 하위 원재료를 메뉴 원가에 다시 펼치지 않으므로 현재 계산은 하위 원가를 중복 합산하지 않는다.

### 1.6 우선순위별 문제

#### P0 — 데이터 유실·운영 중단 가능성

1. **전체 자료 덮어쓰기와 동시 작업 충돌** — 확인  
   재고, 품목, 제조, 원가 업로드 화면은 읽어 온 전체 `CafeDataset`을 수정한 뒤 `replace_store_dataset`으로 기존 `store_records`를 전부 삭제하고 다시 넣는다. DB 안에서는 한 트랜잭션이지만, 두 사용자가 각자 오래된 화면에서 저장하면 나중 저장이 먼저 저장된 다른 사용자의 변경을 지울 수 있다.

2. **코드와 Supabase 컬렉션 제약 불일치** — 확인, 운영 반영 여부 미확인  
   앱 코드는 `purchaseLots`, `productionBatches`, `bottleStates`, `auditLog`를 공용 저장 대상에 포함한다. 저장소의 마이그레이션 파일에 있는 `store_records.collection` CHECK 제약에는 이 네 컬렉션이 없다. 운영 DB에 별도 수동 변경이 없다면 전체 저장이 실패할 수 있다. 운영 DB를 읽기 전에는 실제 운영 상태를 확정할 수 없다.

3. **가져오기·복원의 교체 범위가 큼** — 확인  
   엑셀 가져오기와 JSON 복원은 전체 자료를 교체한다. 화면에 사전 검사는 있지만 자동 백업을 필수로 만들거나 서버 버전 충돌을 검사하지 않는다.

#### P1 — 계산·이력 신뢰성 문제

4. **같은 날짜 안의 순서를 표현하지 못함** — 확인  
   재고 이벤트와 판매는 날짜만 저장하고 시각·순번이 없다. 마지막 실사와 같은 날짜의 입고·판매는 계산 조건상 실사 이후 기록인지 판단할 수 없어 제외될 가능성이 있다. 실제 순서를 복원할 근거가 없다.

5. **삭제가 취소·정정 이력을 대체함** — 확인  
   판매와 재고 기록은 실제 행을 삭제할 수 있다. 감사 로그는 일부 전체 자료 저장 흐름에만 있고, 판매 삭제에는 별도 취소 원장이 없다. 제조 후 환불처럼 매출 취소와 재고 복구가 다른 상황을 표현할 수 없다.

6. **매입·발주·입고가 분리되지 않음** — 확인  
   현재 입고 저장은 구매 로트·재고 증가·가격 이력을 동시에 만든다. 주문했지만 아직 받지 않은 상태나 부분 입고를 표현할 독립 발주/매입 문서가 없다.

7. **제조 저장의 중복 요청 방지 부족** — 확인  
   배치 생성 버튼에 저장 중 잠금이 없고, 요청별 고유 멱등 키를 서버에서 검사하지 않는다. 한 번의 전체 교체는 원자적이지만 반복 클릭·네트워크 재시도에 대한 별도 보장은 없다.

8. **정밀도 정책이 일관되지 않음** — 확인  
   판매·원가의 일부 계산은 `decimal.js`를 사용하지만 재고 합산, 발주량, 폼 값과 다수 금액 계산은 JavaScript `number`를 사용한다. ml/g 소수 수량이 누적될 때 허용 오차와 반올림 위치가 문서화되어 있지 않다.

9. **논리 관계를 DB가 보장하지 않음** — 확인  
   JSON payload 구조라 `materialId`·`menuId` 관계를 DB 외래키가 막지 못한다. 전체 파일 가져오기에는 검증이 있지만 개별 화면 저장과 동시 변경에 같은 수준의 참조 무결성 검사가 없다.

#### P2 — 기능 중복·사용성 문제

10. **품목 관리가 두 화면에 중복** — 확인  
    `/inventory/items`와 `/costs`가 모두 품목을 추가·수정한다. 두 폼의 필드와 기본값, 중복 감지, 가격 이력 생성 규칙이 다르다.

11. **메뉴·레시피 관리가 원가 화면에 섞임** — 확인  
    `/costs`에서 새 제품과 v1 레시피를 만들 수 있지만 기존 메뉴·레시피를 체계적으로 수정하거나 버전을 올리는 독립 화면은 없다.

12. **품목 등록과 재고 입고의 구분은 있으나 화면 연결이 약함** — 확인  
    품목 설정은 수량을 바꾸지 않고 재고 기록은 품목 기본 정보를 바꾸지 않는다. 책임은 분리돼 있지만 기존 사이드바가 두 업무를 별개 메뉴로 보여 주고 품목 상세 연결이 없다.

13. **모바일 표 중심 UI** — 확인  
    작은 화면에서 가로 스크롤 표가 대부분 그대로 남는다. 하단 고정 메뉴로 실제 화면 높이가 줄고, 반복 실사 입력·연속 입고를 위한 카드형 빠른 입력은 없다.

14. **빈 상태와 로딩 상태 혼동** — 확인  
    여러 화면이 `data === null`을 로딩 중과 실제 자료 없음에 함께 사용한다. 네트워크 오류도 별도 상태 없이 빈 화면처럼 보일 수 있다.

15. **대시보드 용어와 지표 부족** — 확인  
    현재 대시보드는 판매, 공헌이익, 운영비, 부족 재료를 보여 주지만 재고 평가액·최근 매입액·실사 차이는 없다. 매입액·재고 자산·매출원가를 구분해 보여 주는 구조도 아직 없다.

## 2. 변경한 카테고리 및 화면

PHASE 1에서는 운영 배포 화면을 변경하지 않았다.

이 변경은 PHASE 3에 해당하며 PHASE 1 완료 시점에는 **구현 완료로 판정하지 않는다**.

## 5. 기존 기능과의 호환성

### 유지해야 할 식별자와 계산 기준 — 확인

- `materialId`, `menuId`, `recipeVersion`, `saleId`, `eventId`, `batchId`를 유지해야 한다.
- 판매 당시 원가 스냅샷은 과거 사실이므로 다시 계산해 덮어쓰지 않는다.
- 초기재고와 실사 기준 수량은 출처가 불분명하면 새 값으로 재생성하지 않는다.
- `/inventory`, `/inventory/items`, `/inventory/new`, `/inventory/batches`, `/costs` 기존 URL은 유지하거나 명시적 호환 이동을 제공한다.
- 기존 Excel/JSON 백업 형식은 새 형식이 안정될 때까지 읽을 수 있어야 한다.

### 통합 가능한 영역 — 제안

- 품목 마스터 수정은 `재고 관리 > 품목 관리` 한 곳으로 모으고 `/costs`에서는 품목 선택과 가격 이력만 다룬다.
- 재고 이벤트 조회·실사·입출고는 동일 원장을 다른 업무 탭에서 필터링해 보여 준다.
- 제조 배치는 재고 관리 안에서 접근하되 기존 `/inventory/batches` URL을 유지한다.
- 메뉴·레시피 편집은 독립 카테고리로 분리하고 원가 화면은 계산 결과를 참조한다.

## 6. 테스트 결과

### 이번 조사에서 확인한 것

- 라우트·컴포넌트·저장 함수·계산 함수·마이그레이션 파일을 정적 분석했다.
- 단위 테스트: `3개 파일, 15개 테스트` 통과
- TypeScript 검사: `tsc --noEmit` 통과
- ESLint 정적 검사: 오류·경고 없이 통과

### 아직 검증하지 않은 것

- 운영 Supabase의 실제 CHECK 제약과 마이그레이션 적용 상태
- 운영 자료의 실제 품목·판매·재고 연결 건수
- 동시 사용자 충돌 재현
- 첨부 지시문의 테스트 A~J 전체
- 진행 중 재고 통합 화면의 브라우저·모바일·뒤로가기 검증

따라서 PHASE 1은 구조 조사 완료이며, 기능·데이터 마이그레이션 검증 완료가 아니다.

## 7. 데이터 유실 또는 운영 위험

| 위험 | 현재 영향 | 실행 전 필요한 조치 |
|---|---|---|
| 전체 자료 교체 중 오래된 화면이 최신 자료를 덮어씀 | 높음 | 서버 버전 확인과 충돌 거절, 컬렉션별 저장으로 전환 |
| 운영 DB 제약과 코드 컬렉션 불일치 | 높음 | 읽기 전용 스키마 확인 후 추가형 마이그레이션 작성 |
| 가져오기·복원 실수 | 높음 | 자동 백업, 변경 건수 미리보기, 확인 문구, 롤백 경로 |
| 판매·재고 행 삭제로 원인 추적 불가 | 중간~높음 | 취소/정정 상태와 반대 이벤트 도입 후 삭제 제한 |
| 같은 날 실사와 이동 순서 불명 | 중간 | 발생 시각·기준 시점 추가, 기존 기록은 날짜 기반으로 보존 |
| 중복 배치·입고 요청 | 중간 | client token/원본 문서 ID 고유 제약과 저장 중 잠금 |

운영 데이터 변경이 필요한 다음 단계에서는 반드시 먼저 백업 방법, 대상 행 수, 적용 SQL, 롤백 SQL을 제시하고 승인을 받아야 한다.

## 8. 아직 구현하지 않은 기능

- 발주·매입·입고 확정의 분리
- 불변 재고 원장과 취소/정정 이벤트
- 기준 시점이 있는 재고 실사와 승인 절차
- 판매 취소·환불 및 재고 복구 판단
- 서버 멱등성·낙관적 잠금·동시성 충돌 화면
- 정규화된 품목·레시피·재고·배치 테이블
- 메뉴·레시피 전용 관리와 버전 전환
- 실제 원가와 이론 원가 비교
- 재고 평가액·최근 매입액·실사 차이 대시보드
- 모바일 카드형 입고·실사 흐름
- 매장 간 권한 격리 자동 테스트

## 9. 다음 단계 — 단계적 개편 계획

### 안전 선행 단계

1. 운영 DB를 **읽기 전용**으로 점검해 현재 제약, 함수, 정책, 컬렉션별 건수만 확인한다.
2. 운영 전체 JSON 백업과 복구 리허설을 별도 테스트 프로젝트에서 수행한다.
3. 데이터 지문을 만든다: 컬렉션별 건수, ID 목록 해시, 참조 누락 수, 재고 계산 결과 해시.
4. 테스트 A~J를 현재 구조 기준 회귀 테스트로 먼저 고정한다.

### PHASE 2 — 공통 데이터 구조 정리

제안은 기존 JSON 자료를 즉시 없애는 방식이 아니라 **추가형·병행형**이다.

1. 기존 ID를 그대로 보존하는 정규화 테이블을 추가한다.
2. 품목, 단위 환산, 구매 문서, 입고, 재고 이벤트, 실사 세션, 배치, 레시피 버전, 판매 정정의 책임을 분리한다.
3. `store_id`는 서버가 로그인 사용자 권한에서 결정한다.
4. 재고 이벤트에 `occurred_at`, `source_type`, `source_id`, `client_token`, `reversal_of`, `created_by`를 추가하고 고유 제약을 둔다.
5. 기존 JSON을 읽는 기능을 유지한 채 새 구조에 복사하고, 건수·ID·계산 결과가 같을 때만 읽기 경로를 전환한다.
6. 전환 후에도 일정 기간 기존 백업을 보존해 롤백할 수 있게 한다.

이 단계의 실제 DB 변경은 별도 승인 대상이다.

### PHASE 3 — 재고 현황·품목 관리 통합

1. 진행 중인 재고 탭을 정리해 현황, 품목 관리, 입출고, 실사, 발주, 제조 배치로 확장 가능한 구조를 만든다.
2. 첫 노출은 현황·품목·입출고 세 탭으로 제한하고 실사·발주·제조는 보조 메뉴로 둔다.
3. 품목 상세 URL을 추가하되 기존 URL과 북마크를 보존한다.
4. 조회·검색·탭 이동은 데이터를 쓰지 않도록 자동 테스트한다.

### PHASE 4 — 프렙 및 레시피 연결

1. 배치 레시피와 실제 투입량을 분리한다.
2. 생산 확정 시 투입 차감·완성 증가·원가 이력을 서버 트랜잭션 한 번으로 처리한다.
3. 자체 제조 베이스는 메뉴 원가에서 완성품 단가만 사용해 하위 원가 중복을 막는다.

### PHASE 5 — 판매와 재고 연결

1. 현재 판매 스냅샷을 보존한다.
2. 판매 이론 사용량은 하나의 원천만 사용한다. 이벤트 원장으로 전환할 경우 기존 직접 차감 계산을 동시에 사용하지 않는다.
3. 취소·환불과 재고 복구를 별도 선택으로 기록한다.

### PHASE 6 — 비용 및 수익성

1. 매입액, 재고 자산, 매출원가 추정치, 운영비를 서로 다른 지표로 표시한다.
2. 재료비만 반영한 이익은 `재료비 차감 이익`, 결제수수료 등 변동비까지 반영한 값은 `공헌이익`으로 표시한다.
3. 데이터가 부족한 값은 0이 아니라 `미집계` 또는 `추정치`로 표시한다.

### PHASE 7 — 모바일·통합 테스트

1. 재고 현황은 카드형 목록으로 품목·잔량·부족 상태를 우선 표시한다.
2. 입고·실사는 숫자 키패드, 연속 입력, 저장 중 잠금, 실패 후 입력 보존을 제공한다.
3. 테스트 A~J와 기존 URL·백업 복원·권한 격리 회귀 테스트를 모두 통과한 뒤 배포한다.
